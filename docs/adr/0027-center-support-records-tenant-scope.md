# Center 支撑业务事实直接绑定 Tenant

状态：已决定，2026-11-14

## 背景

设备凭据、设备连接观察和注册资格绑定都描述某个 Tenant 内的设备业务事实。仅通过 `device_id` 或 `ownership_id` 间接取得归属，会让模型查询、复合外键和协议热路径无法直接验证当前 Tenant，也容易在跨客户转配或恢复核对期间产生不完整的查询条件。

## 决策

以下 Center Model 直接保存不可变的 `tenant_id`，并由 ORM 的租户字段声明参与查询和持久化：

- `DeviceCredential`：设备接入凭据属于签发时的 Tenant 和使用关系；
- `DeviceConnection`：连接观察属于当前记录对应的 Tenant 和使用关系；
- `DeviceEnrollmentBinding`：注册资格与设备使用关系的绑定属于注册时的 Tenant。

三类记录的 Schema、索引和外键同时使用 Tenant 约束，写入值由已验证的设备或注册资格上下文提供，客户端不能覆盖。对会长期保留的凭据历史和注册绑定，设备只保留不可变的简单 `device_id` 外键；`tenant_id + ownership_id`、`tenant_id + enrollment_id` 复合外键约束其签发时的使用关系和注册资格。连接观察是当前投影，同样以简单 `device_id` 外键配合 `tenant_id + ownership_id` 复合外键，转配时在同一事务中更新到新使用关系。这样既能直接校验记录 Tenant，又不会因历史记录保留而阻塞设备跨 Tenant 转配。协议认证、连接观察和注册详情读取均将 Tenant 纳入条件；转配建立新使用关系时同步更新连接观察和新凭据的 Tenant。

运行节点观察、恢复进度/保全主体和公开注册入口限流仍是安装或协议基础设施投影，它们不代表某个客户业务事实，继续作为已登记的表级例外，不伪造业务 Tenant 字段。

## 取舍

直接绑定 Tenant 增加了三类记录的字段与约束，但让 Model 的归属、索引和数据隔离可被单独检查，减少跨表推断和裸主键访问。历史事实不能强制匹配当前设备 Tenant，否则保留凭据或绑定会阻塞转配；复合约束只放在生命周期稳定的使用关系、注册资格以及当前连接投影上。全新安装基线可以直接采用新结构；旧安装按当前策略拒绝接入，不提供数据转换分支。

## 验收

三库 Schema 必须包含字段、索引、稳定关系的复合外键和设备的简单外键；Model 编译结果必须声明 `tenant_id`；注册、轮换、转配、连接观察、详情分页和 MQTT 认证必须通过同一 Tenant 条件。跨 Tenant 的伪造输入、旧使用关系和未知 Tenant 均应拒绝，转配不得因历史凭据或注册绑定而违反外键。
