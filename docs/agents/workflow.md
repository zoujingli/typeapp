# 工程流程

本仓库适配当前安装的 Matt 工程技能。技能负责流程，本仓库提供固定项目配置；不复制用户机器中的全部技能源码或绝对路径。

## 需求到实施

| 用户目标 | 使用的技能 | 完成条件 |
| --- | --- | --- |
| 澄清方案并记录领域语言 | `grill-with-docs`，组合 `grilling` 与 `domain-modeling` | 决策分支澄清、术语及时记录、需要的决策已落档 |
| 将已有讨论转为规格 | `to-spec` | 完整中文规格发布到 GitHub，标签正确，正文回读一致 |
| 将规格拆为任务 | `to-tickets` | 用户确认纵向切片和阻塞边后，逐项发布并回读校验 |
| 评估待处理需求 | `triage` | 依据证据和维护者方向设置分类与状态 |
| 实现已决定任务 | `implement` | 完成一个可观察行为，验证通过，报告变更与实际限制 |
| 测试驱动实现或集成测试 | `tdd` | 在已约定接口处逐条失败测试、最小实现和验证 |
| 排查故障 | `diagnosing-bugs` | 原因有证据；实现修复遵守用户授权 |
| 审查修改 | `code-review` | 固定比较点，分别审查规范和需求符合性 |

技能是否可用先从当前会话目录或已安装技能确认；缺失时说明准确名称和影响，不假装执行过。没有用户安装要求时不擅自改动个人技能配置。

## 格式

- 规格保留“问题陈述、解决方案、用户故事、实现决策、测试决策、范围之外、补充说明”七部分；用户故事按“作为……我希望……以便……”编号。
- 每个任务描述一条窄而完整的可演示路径，包含父规格、交付行为、验收标准和阻塞关系。依赖必须真正阻止开始，不以同一包或同一目录为由串成无必要的长链。
- 任务正文描述行为与稳定接口，避免具体实现路径和大段代码。每个任务一份草案，汇总表不能代替逐项说明。
- 架构讨论中的候选、已决定要求和已实现证据分开标记。

## 确认与连续工作

只为仍未解决且影响结果的选择询问用户。已经在会话里确定的仓库、语言、跟踪工具和授权继续生效，不为初始化流程再次询问。

to-tickets 的新拆分尚未得到用户确认时，先完成可审阅草案与依赖检查再请用户确认；此前对父规格的同意不自动等于对新拆分的同意。已授权任务的实现与验收顺序按[实施约定](implementation.md#开发顺序)执行，不把任务草案当作实现授权。

单阶段完整交付是总体目标；纵向任务是同一目标的内部工作分解，不是删减或推迟已承诺功能。
