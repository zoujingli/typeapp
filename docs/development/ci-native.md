# 完整原生 CI 的分组与工具链

`native-command.yml` 的完整矩阵对同一提交运行十九个独立 Linux x64 分组：基础构建、HTTP、驱动、查询迁移、模型、事务数据、缓存、队列、调度、独立消费者、可靠性、共存回滚、组件集成、TLS、隔离构建、标准应用、交付归档、封装回滚和系统服务。每组使用锁定 PHP/TypePHP/PHPX，最多十六组并行；各组的 runner、数据库和 Redis 相互独立。一组失败仍保留其他分组的诊断结果，整个工作流不能成功。runner 使用 Ubuntu 24.04，以满足已声明的 SQLite JSON 查询最低 3.38 要求；手动选择隔离构建时只运行对应分组。

可靠性场景覆盖真实 AOF 重启、存储满载、进程停止和恢复；回滚组生成两个版本的 ELF，再对三个数据库运行共存与回滚路径。组件集成组按 `.github/distribution.json` 独立安装全部组件，构建工具和测试组件归开发依赖，生产组件全部进入编译清单；不以固定组件数量代替完整集合校验。各组分别上传 ELF、构建身份与验证报告，分发要求准确主仓 SHA 的成功 `push` CI。

## 固定 SDK 入口

TypePHP 会优先尝试同目录的版本化 `php-config8.x`。`tools/configure-toolchain.php` 根据明确指定的 `php-config` 验证锁定版本、ZTS 头文件与实际 `libphp.so`，生成内容标识的独立 SDK 前缀，使构建始终使用已选择的同一套工具链；其余配置选项转交原配置程序。

独立前缀只包含所选 PHP、头文件和 embed 库的链接，以及固定前缀/库位置的配置入口。工具最后直接调用锁定 TypePHP 的库定位 API，确认它找到同一个真实库。原系统安装保持不变，已有 SDK 内容变化会被拒绝。所有原生与分发工作流复用这个入口。

## Linux runner 上的故障环境

本地默认仍使用容器中的工具链。CI 设置 `TYPE_TEST_EXECUTION=host`，使用当前 runner 已准备的 PHP、SDK 和 Composer；测试 Redis 独立运行在 Docker 中，只向 `127.0.0.10` 至 `127.0.0.13` 的回环地址开放。故障脚本保留原来的真实存储策略、故障动作、断言和标签清理规则，不依赖开发者机器上的预建工具链镜像。

可靠性脚本仍单独创建并清理 AOF 数据卷和网络；共存/集成脚本单独创建可靠队列与缓存实例。CI 每个分组使用独立 runner，同一脚本在组内顺序执行。若回环端口已被占用，Docker 启动失败并进入本轮资源清理，不停止其他进程或容器。

配置检查使用 `actionlint`、ShellCheck 和 Bash 解析。工作流配置、编译成功和实际原生行为分别验证；外部依赖、进程及业务通过与否以对应提交的执行报告为准。Linux ARM64 与 Windows x64 的独立工作流不能用 Linux x64 的结果代替，完整状态见[平台与工具链](platform-support.md)。
