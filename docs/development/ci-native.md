# 完整原生 CI 的分组与工具链

`native-command.yml` 对同一提交运行十五个独立 Linux x64 分组：基础构建、HTTP、驱动、查询迁移、模型、事务数据、缓存、队列、调度、独立消费者、可靠性、共存回滚、十四插件集成、TLS 和隔离构建。每组使用锁定 PHP/TypePHP/PHPX，最多十五组并行；各组的 runner、数据库和 Redis 相互独立。一组失败仍保留其他分组的诊断结果，整个工作流不能成功。runner 使用 Ubuntu 24.04，以满足已声明的 SQLite JSON 查询最低 3.38 要求；不会为旧测试系统降低框架能力门槛。

原先串行工作流的所有 Composer 检查均保留。新增可靠性场景覆盖真实 AOF 重启、存储满载、进程停止和恢复；回滚组先生成两个版本的 ELF，再对三个数据库运行既有共存与回滚路径；完整集成组独立安装十四插件并生成三个数据库的原生产物和采样报告。各组分别上传 ELF、构建身份与验证报告，分发继续要求准确主仓 SHA 的成功 `push` CI。

## 固定 SDK 入口

旧 CI 在系统 `/usr` 前缀下曾同时报告缺少 embed 库和源码转换错误。TypePHP 会优先尝试同目录的版本化 `php-config8.x`，因此只设置共享前缀不足以表达“当前已选择的 ZTS SDK”。`tools/configure-toolchain.php` 根据明确指定的 `php-config` 验证锁定版本、ZTS 头文件与实际 `libphp.so`，生成内容标识的独立 SDK 前缀；其余配置选项仍转交原配置程序。

独立前缀只包含所选 PHP、头文件和 embed 库的链接，以及固定前缀/库位置的配置入口。工具最后直接调用锁定 TypePHP 的库定位 API，确认它找到同一个真实库。原系统安装保持不变，已有 SDK 内容变化会被拒绝。所有原生与分发工作流复用这个入口。

## Linux runner 上的故障环境

本地默认仍使用容器中的工具链。CI 设置 `TYPE_TEST_EXECUTION=host`，使用当前 runner 已准备的 PHP、SDK 和 Composer；测试 Redis 独立运行在 Docker 中，只向 `127.0.0.10` 至 `127.0.0.13` 的回环地址开放。故障脚本保留原来的真实存储策略、故障动作、断言和标签清理规则，不依赖开发者机器上的预建工具链镜像。

可靠性脚本仍单独创建并清理 AOF 数据卷和网络；共存/集成脚本单独创建可靠队列与缓存实例。CI 每个分组使用独立 runner，同一脚本在组内顺序执行。若回环端口已被占用，Docker 启动失败并进入本轮资源清理，不停止其他进程或容器。

配置检查使用 `actionlint`、ShellCheck 和 Bash 解析；调整后还逐项比较了原工作流的 Composer 命令集合，没有遗漏旧检查。外部依赖、进程和全部业务通过与否仍由实际原生执行决定。
