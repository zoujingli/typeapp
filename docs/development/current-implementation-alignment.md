# 当前实现说明

本文描述当前代码的职责、接口和已确定的实现边界，待完成工作集中在[实现规划](../guide/roadmap.md)。

## 职责分工

TypeApp 框架与物联中心的职责分工如下，技术架构定义以[系统架构](../guide/architecture.md)为准：

- TypeApp 是应用框架，物联中心是以 `app` 为业务源的成品案例。
- Plugins 以 `plugin/type-*` 维护组件源码并通过独立子仓分发；组件不反向依赖物联中心业务。
- TypePHP 负责生产 PHP 实现的全量 AOT，Swoole 是通信及基础并发的必需底层；具体角色的接入方式和验收状态分别记录。
- 浏览器端是同一物联中心内的两个业务工作区：独立的平台管理端和默认的 SaaS 用户端；不是两个互相替代的应用，也不是一个混合账号系统。
- Broker 管理保持第三个独立身份域和独立宿主边界；它可以被平台或客户按已授予的只读资源权限观察，但不并入平台或客户账号。

当前并非“整体设计错误”，而是后端身份与业务基础已经形成，站点配置基础已接通，前端管理体验、完整主题偏好和标准项目分发仍需继续汇合。后续不应重新设计账号模型或再造一套通信机制，而应按缺口收敛已有实现。

### Swoole 唯一底层与单程序交付

Plugins 为统一称谓；通信、进程、线程、协程与事件循环必须使用 Swoole 官方能力，进程不可用时使用线程/协程。生产交付为一个程序文件加外置配置，所需原生库由程序携带和管理。决策见 [ADR 0021](../adr/0021-required-swoole-and-single-program.md)。

当前实现已经统一到以下运行边界：

| 范围 | 当前实现 | 责任边界 |
| --- | --- | --- |
| MQTT 服务端 | TCP、TLS、mTLS 与 WebSocket 由同一个 Swoole Server 持有监听和生命周期；WebSocket 端口负责 HTTP 升级及 MQTT 帧 | Broker 保留 MQTT 报文、授权、会话、持久提交和资源预算；不再维护可选网络驱动 |
| MQTT 客户端 | 协程模式使用 `Swoole\Coroutine\Socket`，同步模式使用 `Swoole\Client` | Client 负责 TLS 身份、半包、保活、超时、确认凭据和关闭语义 |
| 持久工作与设备接入 | `PendingCommit`、设备授权和摄取 worker 使用 Swoole Process 管道；HTTPS CRL 使用 Swoole Coroutine HTTP Client | 应用保留有界结果、硬截止、提交未知与远端释放证明；Swoole 负责执行与通信 |
| 跨平台服务入口 | HTTP、WebSocket、TCP、UDP、MQTT 均按目标平台使用 Swoole 官方 Server、Socket、线程或协程能力 | 只在所需原生能力确实缺失时报告启动错误，并记录对应平台验收范围 |
| AOT 与运行包 | 生产 PHP、生成代码和实际生产依赖交给 TypePHP 全量编译；Swoole 为必需运行扩展 | 编译产物与外置配置分离，不能回退 Composer 源码解释执行 |

PSR 消息流与文件流继续保留标准职责；独立协议测试工具不作为生产通信底层。

平台状态统一见[平台与验收](../guide/platforms.md)，运行及产物身份见[平台证据](platform-support.md#当前结果与证据)。每个平台必须以匹配的 PHPX、Swoole 和线程/协程构建完成同一份应用产物验收。

### 平台管理端

平台管理端使用 `admin` 账号域和 `/admin` 页面入口，职责是平台范围的治理：

- 平台人员、平台角色和平台账号角色分配；
- 客户账号、客户状态、密码和会话；
- 租户创建、资料、状态和客户最高管理员绑定；
- 全局设备资产、生命周期和凭据动作；
- 站点设置、系统配置、审计、运行观察和 Broker 资源元数据。

平台角色只决定平台范围的权限。平台身份不会因为管理租户或设备资产而自动获得客户租户的遥测、控制或其他业务权限。平台人员进入客户工作区时，必须使用已授权的模拟登录动作，目标权限只取客户在当前租户的有效成员角色，并保留真实平台来源。

### SaaS 用户端

SaaS 用户端使用 `customer` 账号域和默认 `/` 页面入口，职责是客户自己的业务工作区：

- 选择本人有效的租户成员关系；
- 管理当前租户成员、租户角色和固定权限目录中的授权；
- 管理产品、物模型、设备、设备转移和生命周期；
- 查询当前数据、历史、指令结果、告警、通知和导出；
- 按当前租户范围查询审计、运行观察和允许查看的 Broker 资源。

同一客户账号可以加入多个租户，但成员关系、角色、状态、版本和数据范围都按租户独立保存。切换租户必须重新读取权限、菜单和业务数据，不能把上一个租户的页面状态带入新租户。

### Broker 管理端

Broker 使用独立 `broker` 身份域和自身管理 API。Broker 的节点、资源、运行观察、审计以及 MQTT 接入协议由 Broker 组件/宿主拥有；物联中心只通过明确的公开契约读取或管理允许的业务元数据。Broker 账号不能用来调用平台或客户 API，平台/客户账号也不能隐式取得 Broker 的管理权限。

## 登录与授权边界

当前后端已存在三类认证入口：

| 身份域 | 登录 | 当前用户与权限 | 退出 |
| --- | --- | --- | --- |
| 平台管理 | `POST /admin/auth/login` | `GET /admin/auth/me` | `POST /admin/auth/logout` |
| SaaS 客户 | `POST /customer/auth/login` | `GET /customer/auth/me` | `POST /customer/auth/logout` |
| Broker | Broker 宿主的 `/auth/login` | Broker 宿主的 `/auth/me` | Broker 宿主的 `/auth/logout` |

`app/common/controller/AuthController.php` 负责平台与客户两端的固定入口，`IdentityService` 负责会话和账号域，客户端不能通过请求字段选择数据库表、身份域或模拟身份。客户的 `X-Tenant-Id` 只用于选择本人有效成员关系；平台身份携带租户上下文会被拒绝。

当前初始化是全新模式：不读取旧账号、旧角色、旧支持记录或旧业务路由，也不自动清理已有数据。已有数据库必须由操作者先核对，初始化发现不符合新安装模式时应拒绝继续。

## 两套 RBAC，而不是一套混合角色

`app/common/service/RoleService.php` 当前已经按身份域声明固定权限目录：

- 平台目录包含平台人员、平台角色、客户账号、租户、系统配置、平台设备、审计、运行观察和 Broker 元数据。
- 客户目录包含成员、租户角色、产品与物模型、设备、遥测、指令、历史、告警、通知、导出和设备转移。
- 权限节点只能从固定目录选择，不允许运行时创建任意路由、组件名、通配权限或执行代码。

有效权限按以下规则计算：

1. 先确认当前会话、账号和成员状态有效。
2. 平台账号从 `admin_user_roles` 的启用平台角色取权限并集。
3. 客户账号在指定租户从启用成员关系和租户角色取权限并集。
4. 后端每个动作再次检查权限；菜单和按钮隐藏只是辅助体验，不是安全边界。
5. 受保护最高管理员和最后有效最高管理员保护在授权事务内执行。
6. 角色、账号、成员和授权写入使用版本检查、授权锁和审计；不能靠停用角色、批量绑定或密码动作绕过授权限制。

当前已实现的管理 API 包括平台人员、客户账号、平台角色、租户、租户最高管理员、客户成员、租户角色和个人资料。客户业务 API 位于 `app/iot/controller`；Broker API 位于 `app/broker/controller`。这些接口的存在不等于所有前端页面已经完成 Vben 原生体验或所有跨平台验收已经完成。

## 菜单和页面归属

后端菜单由 `RoleService::menus()` 按固定权限目录生成，父级只负责导航分组，不增加额外权限。当前分组意图如下：

| 工作区 | 功能分组 | 页面职责 |
| --- | --- | --- |
| 平台 | 身份与租户 | 平台人员、平台角色、平台租户、客户账号 |
| 平台 | 系统管理 | 站点设置、运行配置等平台设置 |
| 平台 | 运维中心 | 设备资产、操作审计、运行概览、Broker 资源 |
| 客户 | 组织与成员 | 我的租户、租户成员、租户角色 |
| 客户 | 物联管理 | 产品、物模型、设备、设备转移 |
| 客户 | 数据与告警 | 历史、告警规则、告警中心、站内通知、导出入口 |
| 客户 | 运维中心 | 操作审计、运行概览、Broker 资源 |

不应把所有功能平铺到一级菜单，也不应为每个页面增加一套新的菜单引擎。新增页面必须归入已有功能分组并复用固定权限目录。详情页、模型版本、设备详情等页面属于父级业务页面的深链接，不单独制造一级菜单。

当前前端路由已经覆盖上述多数页面，但平台和客户仍有部分路由复用同一个 Vue 文件，例如 `admin-users.vue`、`admin-roles.vue` 和 `tenants.vue`。这不代表权限合并；后续应优先澄清页面标题、数据语义、动作权限和默认入口，让两个工作区在 UI 上也保持清楚边界。

## Vben Admin Pro 复用边界

当前前端已经使用 Vben 的 `BasicLayout`、偏好存储、访问状态和 Ant Design Vue，但复用仍不完整：

- `web/apps/web-antd/src/components/app-drawer` 是应用自定义抽屉封装；
- `crud-search-field.vue` 和 `crud-table-actions.vue` 仍是自定义通用外观层；
- 登录页、部分搜索区、行操作和页面级 CSS 仍自行维护；
- `main.ts` 当前关闭了部分 Vben 原生偏好入口，应用名、Logo 与默认首页由站点偏好映射提供（`preferences.ts` 的 `sitePreferenceOverrides()`）；Vben `defaultHomePath` 与 `router.ts` 的根路径及兜底重定向当前均为 `/profile`，默认入口已统一。

后续 UI 标准只有一个：直接复用锁定版本的 Vben Admin Pro 布局、登录、导航、表单、表格、弹层、主题 token 和个人偏好能力；应用只补业务字段、接口、权限和确有业务含义的模型编辑器。除非 Vben 没有对应能力且存在可复现缺口，否则不新增 `app-*`、`crud-*` 或全局样式替代层。删除自定义封装前要逐页迁移并保留行为回归，不为了“看起来像 Vben”重写 Vben 内部机制。

## 站点设置、运行配置与主题配置必须分开

当前 `admin/configuration` 主要读取和保存服务运行配置，例如数据库、Redis、监听器、线程预算和证书字段；它不等同于站点展示设置，也不等同于 Vben 默认主题。

目标边界如下：

- **站点设置**：项目显示名称、公开说明、默认时区及登录页允许公开的信息；默认项目名称为 `TypeApp`。
- **官方网站**：`https://iots.top` 只对应官网和 Docsify 文档站，不是业务 API、客户登录地址、回调地址或 Host 白名单默认值。
- **运行配置**：继续沿用现有字段白名单、脱敏、来源显示、版本、原子保存、审计和重启后生效语义；不能由站点设置写入任意运行键、路径或代码。
- **站点默认主题**：使用 Vben 原生支持且实际接通的主题、布局和导航偏好，由平台保存默认值。
- **个人偏好**：使用者通过 Vben 原生入口调整自己的覆盖值；刷新、重新登录和切换账号/身份时按个人覆盖、站点默认、Vben 缺省的顺序恢复；恢复默认只清除个人覆盖。

当前已落地站点设置的第一条完整链路：`app_site_settings` 在全新安装时写入 TypeApp 默认值，`GET /public/site` 只返回公开白名单，`GET /admin/site` 和 `PUT /admin/site` 受平台 RBAC、版本号、字段校验、授权事务及 `admin_audit` 保护；登录页、Vben 启动偏好和站点设置页已消费该来源。默认值为项目名称 `TypeApp`、官网 `https://iots.top`、说明“物联中心管理平台”、`Asia/Shanghai`、浅色主题与 `#1677ff`。

默认主题链路已扩展到 Vben 实际接通的布局、侧栏、导航、面包屑、标签页和页脚字段；它们与原有主题模式、主题色和圆角共用 `app_site_settings` 的版本、授权事务和审计。个人覆盖保存在当前浏览器，并按身份域、账号及模拟来源隔离；个人资料页的“恢复界面默认”会清除当前作用域覆盖并采用最新站点默认。运行配置仍独立由 `/admin/configuration` 管理，官网地址不参与业务 API、回调或 Host 白名单。完整跨平台和真实浏览器矩阵仍待验收。

## 标准项目、组件和运行包的单一来源

三类交付物必须保持清楚：

1. **主仓业务源**：`app`、`config`、`web`、测试和文档，TypeApp 物联中心的唯一业务来源。
2. **组件分发**：`plugin/type-*` 子目录及其独立分发子仓；可按需安装，组件不包含物联中心业务。
3. **标准项目出口**：`templates/type-project`；应由主仓业务、前端、配置、初始化、构建入口和锁定依赖受控生成，而不是另行手工维护一套业务。

当前 `templates/type-project` 仍是其他业务的独立起点，README 明确物联中心不随该模板分发。生产候选是主仓 `app/`、`config/`、`web/` 编译出的物联中心运行物，不能把通用 User CRUD 模板当作已经完成的物联中心分发，也不能为了修正它恢复 Demo 入口。完整标准项目仍需完成同源生成和真实子仓消费验证。

最终运行包和源项目也不是同一交付物。源项目用于开发和构建；运行包才遵守 `.env` 与单个软件文件入口、`public`、`public/upload`、`runtime/logs` 等部署结构。完成前，不宣称完整单文件软件、真实组件子仓消费或最终重装汇合已经通过。
