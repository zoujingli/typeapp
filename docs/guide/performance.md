# 性能与调优

TypeApp 面向低开销、高并发的应用：把可提前完成的工作放在构建期，以 Swoole 承担网络和并发，在运行期为连接、任务、缓冲与等待设置明确预算。目标是在正确语义和稳定资源占用下充分使用机器能力。

## 性能从哪里来

| 机制 | 对应用的作用 | 使用时关注 |
| --- | --- | --- |
| TypePHP 全量 AOT | 业务、生产组件和依赖编译为原生代码，生产入口直接执行编译结果 | 每次生产代码变更重新构建，具体收益以真实负载测量 |
| 构建期装配 | 提前生成路由、模型、配置和声明操作，减少请求期扫描与动态装配 | 显式声明入口和依赖，保持热路径简单 |
| Swoole 网络与协程 | 复用官方事件循环和可让出的 I/O，让等待期间继续处理其他请求 | 确认操作能让出调度；协程本身不提供 CPU 并行 |
| Swoole 线程与进程 | 按角色和平台能力并行执行、隔离任务 | 每个执行单元有明确状态、连接与停止责任 |
| 按需组合组件 | 只安装业务需要的能力，减少依赖和维护面 | 生产依赖全部参与编译，不通过漏编换取更小产物 |
| 有界资源与流式处理 | 控制连接、队列、缓冲和重试，避免负载上升时内存无界增长 | 同时观察拒绝、超时、尾延迟和资源回收 |

`type-build` 内置 Swoole 模块减少构建准备步骤，不直接提高请求吞吐。Swoole 能力接入、应用性能和部署形式分别验证；环境准备见[环境与依赖](environment.md)。

## 先确定目标，再调整并发

1. **定义真实负载。** 固定请求比例、载荷大小、连接数、数据量、TLS 和数据库；为吞吐、p95/p99 延迟、错误率及内存设置目标。
2. **记录基线。** 使用目标平台的同一原生产物，预热后多轮测量，记录源码、工具链、配置、CPU 与内存。开发 PHP 结果不能替代 AOT 结果。
3. **找到等待与热点。** 区分 CPU 计算、数据库锁、网络、磁盘和排队成本。慢查询优先检查索引、事务范围与访问次数，不能仅靠增加线程掩盖。
4. **一次调整一个因素。** 在实际可用的 Swoole 配置内调整执行单元、连接预算或缓冲，保持业务语义、错误处理和安全校验一致。
5. **验证满载与恢复。** 覆盖慢依赖、过载、取消、断连和停止；确认任务真实结束、资源回收后再增加负载。

增加 worker、线程或副本会放大总连接数和内存。应用的预算应合并计算，并为管理操作、迁移和故障恢复留出余量；作用域、任务树及部署预算见[运行时指南](runtime.md)。

数据库资源池也有驱动边界：不能把逻辑租约复用理解为三库都已完成物理 PDO 连接复用。当前 MySQL、SQLite 的完整物理复用仍待完成，已验证范围见[平台与验收](platforms.md)。事务、连接与结果集由所属作用域使用，不能跨线程或请求共享。

## 当前性能证据

TypePHP 0.9.3 / PHPX 2.9.2 升级已在 macOS ARM64 做同业务、同平台、同负载对照，覆盖短 JSON、MySQL/PostgreSQL/SQLite CRUD、真实锁等待及 1 MiB 文件流。多轮和交替顺序测量未确认持续性能退化，原始方法与结果见[工具链升级验收](https://github.com/zoujingli/typeapp/blob/main/docs/evidence/typephp-upgrade-0.9.3.md)。

这组测量的请求并发为 1，操作速率包含控制器和准备成本，用于升级回归判断，不能作为最大 RPS 或高并发容量。当前尚无覆盖全部平台与业务的峰值吞吐结论，高并发容量需由应用在目标环境按真实负载验收。

后续四平台默认 CI 已通过功能矩阵，但未运行需要显式基准提交的可选性能组。因此不由这次 CI 成功推导性能提升，实际范围见[平台与验收](platforms.md)。

需要复现对照时，按[平台性能方法](https://github.com/zoujingli/typeapp/blob/main/docs/development/platform-performance.md)准备固定源码、工具链和专用测试服务。报告同时记录延迟分位数、吞吐、错误、CPU 与内存，不只展示最快一次结果。
