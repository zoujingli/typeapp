现有能力的需求与入口见[基础能力与验收](capabilities.md)，技术边界见[系统架构](architecture.md)。本文只维护尚未闭合的交付要求；有历史产物记录的结果不自动适用于当前源码与工具链。

RC14 已完成新版 TypePHP/PHPX 与 Swoole 开发快照的四平台默认原生 CI、12 个数据库 profile 静态单程序隔离部署、15 个组件与应用模板的同版本分发、公开消费和下载核验；固定源码与实际范围见[升级验收记录](https://github.com/zoujingli/typeapp/blob/main/docs/evidence/typephp-upgrade-0.9.4.md)。RC13 的原始身份继续保留在[历史平台证据](https://github.com/zoujingli/typeapp/blob/main/docs/evidence/profile-release-20260930.md)。

## 框架开发闭环

下一轮集中成熟现有 15 个组件，目标是让独立应用主要通过 Controller、Service、Model 与配置完成业务，再由 TypePHP 全量编译交付。以下方向已经确定，新增能力尚待实施与验收；RC14 不包含这些新接口。详细契约与验证入口见[框架开发闭环设计](https://github.com/zoujingli/typeapp/blob/main/docs/development/framework-ecosystem.md)。

| 范围 | 已确定的交付 | 完成标志 |
| --- | --- | --- |
| 构建期自动装配 | 统一开发与 AOT 的声明分析，按构造器和显式覆盖生成直接调用；execution 实例归当前作用域 | 独立应用的命令、HTTP 和任务共用装配规则，并发及子作用域不串状态 |
| 原 Service 声明 | 保留原类型、final 与公开签名，把事务/缓存转换到原服务入口 | 标准开发与 AOT 中普通调用、手动构造后调用和类内互调行为一致 |
| 类型化 HTTP | 复用现有校验规则，明确路径参数和输入类，生成业务结果到 PSR 响应的适配 | 输入来源、PATCH、错误码、输出字段及中间件边界在真实 HTTP 中通过 |
| Model 与 Schema | 自动时间字段、关系写入助手、安全冲突写入与常用表结构声明 | 第二业务模块完成三库迁移、CRUD、关系与事务；历史迁移摘要不变 |
| 缓存、事件与任务 | 复用提交后动作、Outbox、Queue 和 Scheduler，补命名数据源及生成注册；统一受管 HTTP 客户端 | 提交、回滚、重复投递、取消与正常停止保留真实结果和资源边界 |
| 工具、模板与教程 | make、离线装配检查、准确模板批次及 Docsify 发布/开发双通道 | 新目录按教程原样完成开发和交付，不由消费测试替用户修补依赖 |

RC 阶段允许集中收敛接口，但调用者、模板、示例、PHPDoc 和升级说明必须一起迁移。四平台各三个数据库 profile 继续使用同一最终程序验收；新版本号及公开发布时间尚未指定。

本轮不新增 RPC、服务发现或配置中心。MQTT 完整规范、HA 故障域及 MySQL/SQLite 完整物理连接复用继续保留专项；它们不阻塞本轮常用闭环的范围判定，也不能因本轮完成就标成已验收。物联中心的全部 UI、真实设备与容量验收另属业务交付。

## 启动与运行收口

全系统审查沿配置、装配、请求、后台角色、停止、数据升级和发布检查了组件及应用调用者。主架构继续采用 TypePHP 全量编译、显式装配和受管作用域。当前 `main` 已补齐下表入口，这些修改未包含在已发布的 RC14 中；原始发现见[系统架构审查](https://github.com/zoujingli/typeapp/blob/main/docs/evidence/system-architecture-audit-20261004.md)，新源码及运行范围见[修复验收](https://github.com/zoujingli/typeapp/blob/main/docs/evidence/system-architecture-fixes-20261004.md)。

| 范围 | 当前实现 | 后续验收与边界 |
| --- | --- | --- |
| 配置预检 | 检查、管理保存和角色启动共用无副作用预检，复用实际 Host/代理、上传与容量约束；非法保存保留原文件 | 生效快照验证字段组合，被进程覆盖的文件值单独查类型；显式连接检查与离线预检分开 |
| 生产诊断 | 内部异常始终记录受控原因、请求 ID 和真实构建身份，请求记录耗时与结果；调试仅增加有限帧 | 后台任务的跨角色关联与完整指标系统仍是独立工作；原生异常未必提供 PHP 源码行 |
| 维护调度停止 | `app:schedule work` 接入信号与停止意图，空闲等待最多每 50ms 复核；在途任务保留真实完成/中断状态 | macOS 三库及真实 Redis 的空闲、在途停止和失锁已验；Windows 控制事件及其他平台需补验 |
| 部署预算 | HTTP 线程、连接池与部署拓扑分别配置；应用数据库入口和后台 Redis 管理器采用统一预算工厂 | 预算是静态分额，实际角色数须受部署监督；MQTT 专用持久连接及其他未经过管理器的连接另计，不能宣称自动约束整个集群 |
| 业务就绪 | `/readyz` 结合接单容量、迁移版本/摘要、兼容门、恢复门和安装身份；`/livez` 不探依赖 | 每执行者缓存有界检查，HTTP 不因后台可选 Redis 故障退出；各协议及后台角色仍按自己的恢复契约验收 |
| 应用升级 | `app:upgrade --check` 与显式停写、备份摘要门已接入迁移锁；macOS ARM64 已从公开 RC13 的三个数据库程序建立真实数据并升级，保留会话、设备和待处理任务 | 只支持当前安装谱系；人工增量夹具仅验证恢复门，其他历史版本及平台须分别验收 |
| 本地文件与缓存 | 日志和本地调度状态共用普通文件校验，接受平台绝对路径；无业务调用者的旧缓存开关明确拒绝，移除无效配置项 | Windows 真实文件/锁/替换仍待验；物联业务缓存未启用，不影响独立应用使用 type-cache |

组件的单项测试通过不能代替这些应用入口验收。PostgreSQL 驱动支持安全重置复用，但物联中心当前 HTTP 池空闲保留为 0；启用物理复用须同时验证隔离和同负载收益，不能仅更改容量值。

## ORM 补齐顺序

当前 `main` 已补充所选 PDO hook 前置检查、模型 `sum/avg/min/max` 和单条 SQL 的 `insertMany`，尚未包含 RC14。下一轮复用 ModelQuery、驱动、作用域和消费者，按下面顺序降低日常业务成本。已有接口及有意边界见[常用能力边界](database.md#常用能力边界)，新增入口属于上面的待实施设计。

| 顺序 | 当前缺口 | 完成条件 |
| --- | --- | --- |
| 1. Model 便捷入口 | 时间字段仍由多个服务手写；关系写入经 definition/loader，已有底层关系算法 | 显式自动时间字段、绑定父 Model 的关系入口；无变化 save 不推进时间/版本，写后关系结果失效，保留租户与 scope 边界 |
| 2. 模型冲突写入 | 底层 Query 已区分 MySQL 任意唯一键冲突和另两库指定目标；Model 缺唯一索引与约束错误支撑 | 补真实唯一索引、结构化冲突和保存点语义，验证租户、软删除、版本与并发 firstOrCreate；不能先查后写冒充原子 upsert |
| 3. 常用结构声明 | 当前迁移保存显式 SQL，Schema 声明尚未实现 | 新迁移生成并冻结三驱动 SQL，普通构建只核对；SQLite 不支持的结构变化明确拒绝，历史迁移及摘要不改写 |
| 4. 新增入口的平台复验 | 本轮新增实现与历史四平台产物身份不同 | 后续发布按同一批次重跑四平台与三库，保留裁剪后缺能力 SDK 的拒绝验证，不用本机通过代替发布门禁 |

MySQL/SQLite 完整会话重置、纯 CRUD 跨租约物理身份观测及复用性能保持独立专项；缺少完整重置时继续安全关闭。MySQL 提交后回调中新事务 UNKNOWN 仍缺对应同产物断连验证，需要复用真实故障装置补齐，不能用其他数据库结果替代。模型重新加载、集合恢复、多态/穿透关系不扩大为本轮必需接口；业务迁移至 Model 仍要独立验收。

## 推进顺序

1. **统一生成与服务入口。** 先打通开发/AOT 的同源生成、构建期装配和原 Service 声明转换，验证并发 scope、生命周期与失败清理。
2. **形成常用业务闭环。** 类型化 HTTP、Model、Schema、缓存与可靠任务共同完成新增模块的完整路径；数据能力可按明确接口并行实施。
3. **同步工具、模板和教程。** 每个接口完成时同步示例与说明，再用全新独立应用原样执行教程；模板版本准备与发布消费不得相互掩盖错误。
4. **完成应用接入与候选验收。** 迁移主仓调用者，汇合现有运行修复，执行四平台、三数据库 profile、公开组件消费与同一最终程序验收；通过后再确定候选发布。
5. **继续独立专项与业务完善。** 协议规范、故障域、物理复用、性能/容量和完整物联体验保持各自的验收边界与真实证据。

基础能力可沿已有接口独立推进；每次发版仍须重新通过四平台单程序门禁。UI 和业务缺口保持自己的验收责任，不能用框架组件测试代替。

每项结果以实际命令退出、协议响应、业务状态和资源释放为判断依据。PHP 行为检查、AOT 编译成功、原生行为通过和完整交付分别判定；缺少运行结果的能力明确保留待验收状态。
