## 框架开发闭环

本轮集中完善现有 15 个组件，让独立应用主要通过 Controller、Service、Model 与配置完成业务，再由 TypePHP 全量编译交付。开发分支已实现下表接口，正在完成原生程序及发布矩阵验收；RC14 不包含这些新接口。详细契约与验证入口见[框架开发闭环设计](https://github.com/zoujingli/typeapp/blob/main/docs/development/framework-ecosystem.md)。

此前物联中心统一装配于 2026-10-06 通过同一完整 AOT 程序的 Darwin arm64 shared embed 本机验收：生产诊断、开发模式边界、应用三库及调度、独立导出三库、主仓候选入口、Broker 证书/CRL、真实 TLS 设备 MQTT 与恢复均通过，原始身份与范围见[物联中心统一装配](https://github.com/zoujingli/typeapp/blob/main/docs/development/iot-application-assembly.md#验证入口与限制)。这项结果不代表 RC19 三平台九个静态单程序或新版本公开消费，教程第二业务模块及发布矩阵继续独立验收。

本轮不新增 RPC、服务发现或配置中心。MQTT 完整规范、HA 故障域及 MySQL/SQLite 完整物理连接复用继续保留专项；它们不阻塞本轮常用闭环的范围判定，也不能因本轮完成就标成已验收。物联中心的全部 UI、真实设备与容量验收另属业务交付。

| --- | --- | --- |
| 配置预检 | 检查、管理保存和角色启动共用无副作用预检，复用实际 Host/代理、上传与容量约束；非法保存保留原文件 | 生效快照验证字段组合，被进程覆盖的文件值单独查类型；显式连接检查与离线预检分开 |

## ORM 补齐顺序

当前 RC19 候选已提供所选 PDO hook 前置检查、模型聚合与批量写入，并补齐下表的 Model、冲突写入和 Schema 入口；历史 RC14 不包含这些修改。继续通过原有独立消费者验证真实驱动语义和原生兼容，不把接口实现等同于完整发布验收。已有接口及有意边界见[常用能力边界](database.md#常用能力边界)。

| 顺序 | 当前实现 | 剩余验收与边界 |
| --- | --- | --- |
| 1. Model 便捷入口 | `Table(createdAt/updatedAt)` 管理实例及集合时间；`relation()` 绑定父 Model 并提供关系写入 | 完成三平台 AOT 与独立消费门禁；Windows 仅诊断；无变化 save 不推进时间/版本，写后关系结果失效，保留租户与 scope 边界 |
| 2. 模型冲突写入 | Model 已接入真实唯一索引、结构化约束错误、保存点与 `firstOrCreate()`；两类 upsert 明确保留驱动差异 | 完成各平台租户、软删除、版本及真实唯一竞争验证；UNKNOWN 不重试，不能先查后写冒充原子 upsert |
| 3. 常用结构声明 | Schema 为新迁移生成并冻结三驱动 SQL，普通构建只核对；显式 SQL 继续可用 | 完成三库原生迁移和失败恢复验证；SQLite 不支持的结构变化明确拒绝，历史迁移及摘要不改写 |
| 4. 简洁声明与反向同步 | `table/schema` 在构建期展开为既有类型化模型；MySQL `model:sync` 默认预览、显式写入，保留业务方法和字段策略；BIGINT 按字符串校验完整范围 | 真实 MySQL 已覆盖幂等、增删保护、精确字段、生成列及 Tenant CRUD；继续完成整个模型编译路径的全量 AOT，局部精确字段探针不代表整套通过 |
| 5. 新增入口的平台复验 | 本轮新增实现与历史四平台产物身份不同 | 后续发布按同一批次重跑三平台与三库，Windows 保留诊断，保留裁剪后缺能力 SDK 的拒绝验证，不用本机通过代替发布门禁 |

MySQL/SQLite 完整会话重置、纯 CRUD 跨租约物理身份观测及复用性能保持独立专项；缺少完整重置时继续安全关闭。MySQL 提交后回调中新事务 UNKNOWN 仍缺对应同产物断连验证，需要复用真实故障装置补齐，不能用其他数据库结果替代。模型重新加载、集合恢复、多态/穿透关系不扩大为本轮必需接口；业务迁移至 Model 仍要独立验收。

## 业务应用

物联中心使用框架公开接口，以下任务不纳入 ORM 组件内部，也不作为其他应用独立安装框架的前置条件。

物联中心采用 [Platform / System / Center 架构](https://github.com/zoujingli/typeapp/blob/main/docs/development/iot-control-client-design.md)：Platform 负责平台与客户、公共菜单和全局 MQTT 运维，System 管理当前 Tenant 的独立身份及设置，Center 共用其会话处理设备与原始通信。当前三库管理 HTTP、恢复状态机、全量 AOT、无源码运行、真实 PostgreSQL 同步/TLS MQTT 已在 macOS ARM64 完成；正式平台/profile 矩阵和完整登录后浏览器页面仍未闭合。[历史候选与 Demo 记录](https://github.com/zoujingli/typeapp/blob/main/docs/evidence/iot-redesign-20261024.md)只证明原源码和产物，不作为当前版本通过依据。

## 推进顺序

1. **统一生成与服务入口。** 先打通开发/AOT 的同源生成、构建期装配和原 Service 声明转换，验证并发 scope、生命周期与失败清理。
2. **形成常用业务闭环。** 类型化 HTTP、Model、Schema、缓存与可靠任务共同完成新增模块的完整路径；数据能力可按明确接口并行实施。
3. **同步工具、模板和教程。** 每个接口完成时同步示例与说明，再用全新独立应用原样执行教程；模板版本准备与发布消费不得相互掩盖错误。
4. **完成应用接入与候选验收。** 迁移主仓调用者，汇合现有运行修复，执行三平台、三数据库 profile、公开组件消费与同一最终程序验收；Windows 只保留诊断，通过后再确定候选发布。
5. **继续独立专项与业务完善。** 协议规范、故障域、物理复用、性能/容量和完整物联体验保持各自的验收边界与真实证据。

基础能力可沿已有接口独立推进；每次发版仍须重新通过三平台单程序门禁，Windows 保持诊断。UI 和业务缺口保持自己的验收责任，不能用框架组件测试代替。

每项结果以实际命令退出、协议响应、业务状态和资源释放为判断依据。PHP 行为检查、AOT 编译成功、原生行为通过和完整交付分别判定；缺少运行结果的能力明确保留待验收状态。
