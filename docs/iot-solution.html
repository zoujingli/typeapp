01 / Architecture

工作区独立，基础设施共用

账号域、登录会话与 RBAC 分开。控制端的跨客户管理使用明确的平台权限；客户端每次请求核对当前成员关系与租户范围。

CONTROL / #/admin

控制端

  • 平台人员、角色、权限与客户工作区
  • 注册资格签发、期限、额度与停用
  • 设备目录、应用管理、撤权与重新分配
  • 站点配置、平台审计与运行观察
CLIENT / #/profile

客户端

  • 当前租户的成员、角色与权限
  • 查看注册资格，管理已获授权的设备
  • 维护接入应用与密钥，逐设备授予通信权限
  • 查看连接、授权生效状态及本客户审计
02 / Authorization

从注册资格到当前关系授权

  1. 签发资格控制端指定客户、注册额度及期限，经受控渠道交付授权码。
  2. 设备注册校验客户、设备标识与授权码，在同一事务占用额度并交付设备凭据。
  3. 应用授权客户创建独立应用，将接收、发送和订阅权限绑定到设备当前使用关系。
  4. 原始通信每次收发核对身份、关系及权限，在准确 Topic 范围内路由原始字节。
身份使用入口授权边界
后台人员独立后台登录、HTTP 管理 API平台或当前租户的 RBAC；人员退出不自动撤销应用密钥
设备公开注册后，以独立凭据连接 MQTT当前有效使用关系及本设备原始消息 Topic
接入应用以独立应用凭据连接 MQTT逐设备授予 receive/send/subscribe；订阅必须同时允许接收

分类是可选管理资料，不决定注册资格或通信协议。新设备不会自动继承同一客户其他设备的应用权限；新使用关系也不继承旧关系授权。

设备换客户时，如何避免旧身份继续访问？

先结束旧使用关系，隔离旧凭据、连接、订阅、持久会话、retained 与待投递状态。只有隔离完成后，目标客户才可确认接收并取得新凭据；目标应用需要重新授权。节点不可达时保持待处理，接口保存成功不等于全部旧连接已经断开。

原始通信包括哪些处理？

系统负责认证、范围检查、协议收发、资源预算和持久协议状态。载荷不经过物模型解析，不产生遥测历史、统计或告警，也不执行业务指令编排。MQTT 确认与设备业务执行结果不同，客户业务系统自行定义消息内容和应答。

03 / Native Delivery

一个主程序，加外置配置

按操作系统、CPU 和数据库 profile 选择一个程序。非系统原生库静态链接，普通启动不释放运行库；部署机无需另装 PHP、Composer、Node 或 Swoole。

显式安装前端

首次安装同时初始化空库并生成 public/。升级替换程序后，显式更新页面，保留上传及非托管文件。日常启动只读取已安装资源。

# 已完成数据库升级后更新页面
./type-app web:install --force
./type-app serve

完整首次安装参数见部署教程，已有数据库不要重复初始化。

外部服务与持久数据

HTTP 管理支持 SQLite、MySQL、PostgreSQL；可靠设备 MQTT 需要 PostgreSQL 严格同步后端，维护调度使用 Redis。数据库服务、TLS 证书、备份、日志及运行生成数据仍由部署者管理。

同一程序可启动多个明确角色，由监督器管理。一个程序文件不表示所有角色自动启动，也不表示运行后不产生数据文件。

为什么采用 Swoole？需要单独部署吗？

Swoole 提供成熟的网络通信、协程、线程及事件循环，框架据此管理并发、截止和资源收尾，减少重复实现底层机制。它随原生程序交付，不需要在部署机安装扩展或独立 Swoole 服务。TypePHP 仍是编译核心，Swoole 不负责业务授权或持久化语义。

开发、正式与演示环境有什么区别？

APP_ENV=dev/prod/demo，默认 prod。demo 保留查询、登录、退出及必要安全审计，HTTP 与命令入口分别拒绝业务写入。环境来自外置配置，修改后重启；没有单独的演示账号体系。正式和演示环境均关闭开发调试。

旧安装中的历史数据怎么处理？

停服、备份和预检后，通过显式升级转换旧设备关系，保存原模型、旧任务及转换来源。无法核实身份或隔离结果的设备保持隔离；旧业务表不清空，现行后台不再开放退役处理入口。旧版本原始证据保持原身份。
