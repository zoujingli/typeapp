# typeapp 项目标准

TypeApp 是以 TypePHP 全量编译、Swoole 驱动运行、Plugins 组合能力的 PHP 应用框架。TypePHP 是构建期的 AOT 编译器，Swoole 是通信与并发运行的必需基础，Plugins 是 Composer 管理的 `type-xxxx` 框架组件。编译输入与运行依赖分别描述，具体关系见[系统架构](../guide/architecture.md)。运行时直接复用 Swoole 官方机制，减少项目自行实现运行时的开发与维护成本；角色接入和平台验收状态分别记录。

物联中心是本仓库的成品案例，不是框架本身；框架说明提及它时只作为案例。其他业务用 `type-project` 创建独立应用，按需安装组件。开发目标是在完整功能、正确语义和安全边界成立的前提下，减少运行开销、依赖和使用步骤；效率结论必须有可复现测量，不能将目标写成已经优于所有框架的事实。

## 命名与兼容边界

- 项目名称、仓库名称与地址统一使用小写 `typeapp`，仅描述文案可使用 `TypeApp`。GitHub 主仓为 [`zoujingli/typeapp`](https://github.com/zoujingli/typeapp)，按 Apache-2.0 公开，直接在 `main` 开发。
- 主仓 Composer 名为 `zoujingli/typeapp`，遵守 Composer 小写命名规则；它是聚合项目，不是组件包。
- 组件目录、Composer 包与分发子仓继续使用 `type-xxxx`，例如 `plugin/type-core`、`zoujingli/type-core`。应用模板仍为 `type-project`，已有 `Type\` 公开命名空间和 `type` 命令不变。
- `type-app.json` 构建配置名、已有 `build/.../type-app` 二进制路径、资源标识及本地检出目录属于兼容性标识，不用项目更名顺带改变部署契约。应用名称默认使用 `typeapp`，使用者明确配置的 `APP_NAME` 仍优先。
- 说明与可执行配置统一使用当前主仓地址。当前架构与使用文档只描述有效规则和实际能力，未完成目标维护在[实现规划](../guide/roadmap.md)；需求协作遵守[需求跟踪约定](../agents/issue-tracker.md)。

## 源码公开与完整交付

主仓、全部 Plugins 分发子仓和应用模板公开提供源码。第一方代码、文档、示例、测试与配置统一采用 Apache-2.0；各仓库附完整 LICENSE 和适用 NOTICE，第三方材料保持原有许可证与来源。仓库简介复用对应 Composer 清单的 description，写清组件实际职责，不声明未经验证的兼容性或性能。

源码基线可以按用户明确要求先发布，已知功能缺陷与未完成能力如实说明并在发布后修复；不把源码可获取等同于稳定版本或完整交付。正式版本与部署承诺继续遵守全量 AOT、真实行为和目标平台验收。公开前核对发布文件范围、凭据及许可材料；生产数据、私钥和秘密配置不进入源码仓库。

公开组件通过 HTTPS Git 地址读取，使用者无需分发 SSH 私钥；写入权限使用独立凭据。组件映射取自 .github/distribution.json，模板映射取自 .github/template-distribution.json。

## 路径与环境可移植性

- **文件中不硬编码绝对目录。** 新增或修改的源码、脚本、配置、模板、文档、任务正文和入仓验收记录使用项目相对路径、配置相对路径或明确的逻辑基准；不得写入当前电脑的用户目录、检出位置、SDK安装目录、包管理器前缀或磁盘盘符。临时准备脚本同样遵守。
- **执行时解析真实位置。** 项目位置由脚本自身位置或显式项目根确定，PHP使用`__DIR__`等位置基准，外部SDK和工具通过已校验配置、环境变量或平台探测定位。相对路径必须说明基准，切换工作目录不改变目标；解析出的本机绝对位置只用于必要的执行和身份核验，不当作其他电脑的默认配置写回文件。
- **记录与机器布局分离。** 入仓证据使用相对文件标识、依赖名称/版本和内容摘要；外部依赖按逻辑来源描述，不复制本机路径或包含本机路径的原始命令/策略。运行报告保存于任务专用输出目录；版本化文档只保留可复用方法、当前边界与必要来源。
- **完成前检查。** 检查本次写入文件中是否残留本机绝对目录，并核对相对路径基准、含空格路径和不同工作目录的解析；涉及执行路径变更时运行相应入口验证。文档内本地链接使用相对链接。

## 主分支开发与临时资源

- **固定开发位置。** 日常开发直接使用主仓原始检出目录的 `main`，停用额外 Git worktree；命令行、Codex 任务及子代理均不自动创建或切换到额外 worktree。开始修改前核对 `git worktree list`、当前目录、分支及未提交内容。若任务落在旧 worktree，先保全其修改并核对提交归属，再回到主仓继续；保留历史分支引用不等于继续在其中开发。
- **并行共享主仓。** 可并行的任务在同一主仓按文件和责任明确分工，重叠修改与 Git 暂存、提交顺序执行。全量编译、容量及故障测试等高资源作业同时只运行一项。独立安装、无源码部署等验收仍用必要的隔离目录和真实依赖，结束后回收，不为隔离验收另建开发 worktree。
- **临时资源有所有者。** 每项任务用 `mktemp -d` 或工具等价入口在项目 `build/` 下建立专用目录，登记所启动进程、端口、容器、测试数据库和生成目录。脚本通过 `finally`、`trap` 或等价退出处理覆盖成功、失败和中断；阶段完成即清理，不等多个任务堆积后再处理。启动前评估磁盘余量，复用锁定依赖及已就绪 SDK，避免重复拷贝依赖、持续空转或留下无人使用的预览服务。
- **证据先保全。** 清理前保存必要原始报告、失败日志、源码/锁/工具链/产物身份及摘要；未解决故障保留最小复现所需输入和准确产物。需要释放原位置时，先压缩归档到项目 `.cache/` 下的专用保留目录，逐文件回读校验，并记录原相对路径、归档摘要和恢复方法。原始证据不改写，未提交修改另行保全；可重建的编译中间文件、重复安装副本及测试数据不长期保留。重建产物不能冒充原验收产物。
- **精确清理。** 先核对目标归属、进程使用情况和真实路径，再删除本任务已结束的临时项；停止容器前核对自动移除设置和挂载卷，需保留的数据先备份。递归清理不跟随符号链接，不对主仓根、用户目录、整个共享缓存或其他项目执行宽泛删除，也不使用全局容器清理。用户数据、秘密配置、日常服务、当前 SDK 和后续必需的验收材料保留。既有遗留项按用户授权的范围清理，仍需先保护唯一内容。
- **完成条件。** 结束时确认本任务临时进程已退出、监听端口已释放、临时目录及测试资源已回收，并报告释放空间和明确保留项。归档只保留必要的一份；需要继续保留大文件时写明用途和解除条件。验收证据保全与资源清理同属交付，清理不降低全量编译或真实行为验收门槛。

## 100% 全量编译门槛

1. **完整范围。** 框架、业务、生成代码以及实际安装的全部生产 PHP 依赖一起交给锁定 TypePHP 编译。开发测试工具不因开发安装而变成生产依赖；生产角色需要的实现必须全部纳入，不以移入开发依赖规避编译。
2. **零漏编。** 从声明源码、Composer 生产依赖和生成入口形成可审计清单；不得靠删除难编译功能、排除生产文件、空壳或 stub 替代实现来通过。第三方适配限定版本、原文件摘要、替换次数和原因，适配后仍保持完整实现与行为等价。
3. **语言基准。** 按[锁定 TypePHP 语法](../standards/typephp.md)设计显式入口、类型、回调与生命周期。PSR 约定保留公开协议，不能为模拟 PHP 宽松语义增加通用运行时猜测层。
4. **无源码回退。** 原生部署通过已编译入口执行，运行包不依赖业务 PHP 文件、Composer 自动加载、运行时 `eval` 或临时解释补齐功能。编译期受限配置与启动期数据分离；PHPX、libphp 和实际原生扩展是运行依赖，不等于业务源码解释回退，也不能被宣传为无任何运行时依赖。
5. **同一产物验收。** 记录源码提交、锁定依赖、工具链、平台/架构、源码清单、编译产物摘要和运行结果。PHP 检查不代替 AOT，编译成功不代替实际业务、异常、清理和无源码部署验证。
6. **证据与目标分开。** 100% 指全量生产实现的编译覆盖门槛，不等于测试覆盖率、所有 PHP 包兼容或所有平台已验证。按目标 OS/架构及 MySQL、PostgreSQL、SQLite 的真实语义验收；未验证项明确保留，旧提交或其他平台的成功不能为当前完整交付背书。
7. **官方内置库例外。** 只有随固定 Swoole 扩展提供的官方内置 PHP 库允许按官方机制加载。其源码版本、内容摘要、构建开关及实际承载模块纳入同一产物身份；该库仍是 PHP 实现。框架、业务、生成代码和其他生产依赖继续全量 AOT，不开放任意 PHP 文件或第三方源码解释回退。

以上延续[应用级整体 AOT 决策](../adr/0002-application-aot.md)与[声明/配置边界](../adr/0003-static-declarations-and-runtime-config.md)。工具版本取自当前锁文件，不另设一份可漂移的版本清单。

## 极简与效率

- **最小接口。** 先复用明确责任的现有模块；只为真实职责、变化点或消除重复增加抽象。简单业务无需叠加透传层、万能管理器、通用适配器或无调用者的扩展接口。
- **Swoole 成熟基准。** 通信及基础并发必须使用 Swoole 官方能力；进程不可用时采用官方线程/协程，保持相同业务职责，不按操作系统名称拒绝整个应用。同步风格网络调用也须由 Swoole 承担，迁移删除旧网络驱动及相关配置、代码和使用说明。线程、协程、通信及 I/O 改造遵守 [Swoole 复用标准](swoole-reuse.md)：直接沿用原生 API 和配置，复核最新官方能力并锁定构建身份；必要编译适配有实证缺口及撤除条件。
- **简化部署。** 交付一个目标平台程序文件及外置配置；PHPX、libphp、Swoole 等实际原生依赖由程序携带并自动管理，应用数据和日志在运行时按需创建。用户无需逐项安装运行库或维护多套启动器。目录包、归档和单文件程序分别记录实际完成状态，验收要求见[构建与部署](../guide/deployment.md#单程序交付约定)。
- **编译期完成静态工作。** 依赖装配、路由、模型映射与声明在构建期显式生成；请求和任务热路径只执行必要业务。业务组件按需安装，不反向依赖物联中心应用。
- **有界资源。** 连接、并发、队列、流缓冲、缓存、日志、重试与等待具有明确预算和所有者，成功、异常、取消和退出路径都回收。吞吐提升不能靠无限排队、关闭校验或静默丢弃错误获得。
- **性能证据。** 优化前后使用相同功能、数据量、负载、平台、依赖和测量方法，记录预热、样本/重复次数、吞吐、p50/p95/p99 延迟及内存/CPU等相关资源消耗。优先定位真实热点；接受优化须同时证明目标指标改善、公共语义不变、相关原生回归无退化。
- **保持标准与可读性。** 遵守[代码与 PHPDoc](coding.md)、[结构](structure.md)和[测试](testing.md)规范。极简减少概念和维护成本，不删减授权、数据一致性、错误处理、测试或用户已确认的功能。

## 修改完成条件

修改前确定涉及的公开行为、编译输入和性能影响；完成后同步调用者、示例、模板、文档及相关前端源码，执行与风险相称的检查和必要原生验收。结果分别说明通过项、跳过项和剩余限制。

按功能以 `前缀(可选范围): 中文描述` 提交；远端推送和发布权限分开处理。具体推送、发布和 CI 执行沿用会话授权，未执行的检查不能计为通过。
