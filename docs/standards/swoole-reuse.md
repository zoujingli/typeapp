# Swoole 原生能力复用标准

TypeApp 以 TypePHP 全量编译、Swoole 官方通信和并发机制为基础。通信、进程、线程、协程和事件循环必须由 Swoole 承担，连接建立、TLS、读写、等待及关闭直接使用原生接口或已验证的 hook，以减少重复开发和平台适配成本。架构依据见 [编译工具与原生运行库](../adr/0015-typephp-and-swoole-foundation.md)及[单程序交付](../adr/0021-required-swoole-and-single-program.md)；最新实现差距见[实现规划](../guide/roadmap.md)，实际验收范围按任务证据记录。

## 选择顺序

1. **先查原生实现。** 追踪当前生产调用者，核对锁定 Swoole 的接口、实现、配置和构建开关。接口可用、组合行为正确、TypePHP 可编译及目标平台验收分别记录。不能只凭类名、文档示例或扩展版本判断缺失。
2. **直接使用已有机制。** 网络接入采用官方 Server、协程 HTTP/Client/Socket；已有 PDO、Redis、文件及独立命令进程调用验证对应 hook，保持既有公开语义。业务入口建立协程上下文，调用方沿用原生等待机制。启用 hook 不等于所有阶段都能让出，原生接口也不自动满足资源上限。
3. **只衔接项目职责。** 在现有组件补编译入口、PSR 转换、作用域、所有者、租约、部署预算和业务语义。删除一层若不会把这些职责散落回调用者，就不保留该透传层。不为“统一”增加另一套 Client、Socket、Timer、Future 或 Driver 管理体系。
4. **实证缺口才适配。** 先检查原生配置、现有资源约束及局部调用调整能否满足要求；仍不能满足时，才在最小接缝修改固定源码。受控补丁不得顺带接管上游线程调度、事件循环或协议引擎。

业务入口统一建立执行上下文，普通业务无需为每次读写创建协程。同步启动、配置加载、编译工具和无法让出的原生阶段明确位置、预算及验证范围；不会把计算包装成 I/O。旧网络驱动、PHP stream socket 通信、应用侧就绪轮询及其可选配置随迁移一起删除，不作为支持方案继续维护。PSR 消息流、文件流及官方 hook 覆盖的标准文件 API 保持各自职责，不能按 `stream` 单词机械删除。

## 责任归属

| 能力 | 直接复用 | TypeApp 保留的职责 |
| --- | --- | --- |
| 线程、协程与等待 | Swoole Thread、Coroutine、Channel、适用的 Lock/Atomic/Timer；各自只在原生支持的线程或协程边界使用。 | 登记的 AOT 入口、PHP ZTS/PHPX 生命周期、执行身份、子任务收尾与额度。 |
| HTTP、WebSocket、TCP、UDP | 原生 HTTP Server/Client、Request/Response、升级与帧、协程 Socket 的连接、TLS、读写、分包、超时与关闭。 | HTTP 的 PSR 边界、升级授权、协议入口装配、连接和消息作用域、业务结果与资源限制。 |
| 文件与原生 AIO | FILE hook、System、原生工作池及完成回调，沿用 PHP 文件与路径语义。 | 上传/导出恢复、受控分块、总在途与字节预算、取消后持有责任；确切的 hook 缺口最小适配。 |
| 数据库与 Redis | 既有 PDO/Redis 扩展及对应的 Swoole hook，按实际驱动选择。 | ORM、显式事务、物理连接复用前的会话恢复、用途池、凭据代次和部署总额。 |
| 队列、调度、MQTT、日志 | 原生等待、Timer、Socket 和文件能力。 | 投递确认与 fencing、计划游标与组内顺序、MQTT 会话/QoS/持久证明、日志脱敏和溢出策略。 |
| 执行隔离 | 可用的 Swoole Process、Thread 与 Coroutine，等待、通信和回收沿用各自官方机制。 | 已编译角色入口、运行身份、有界结果与退出；进程不可用时把角色接入线程/协程，重新核对隔离与停止语义。 |

Swoole 的名称相近不代表职责相同：Coroutine Channel 负责线程内协程等待，Thread Queue 负责线程间数据交换；后者没有容量构造参数，不能仅凭 count() 后 push() 宣称并发容量受限，也不能在业务协程内直接采用阻塞线程的等待方式。先限制生产者、在途数量和字节，再验证唤醒与退出。

Swoole 内置 PHP 库中的 ConnectionPool 等不等于 C++ 原生能力。该官方库沿用 Swoole 请求初始化的加载机制，构建默认 `swoole.enable_library=On`；这是全量 AOT 的唯一明确例外。固定库版本、内容和承载扩展摘要随同产物核对，其他生产 PHP 仍全部编译。当前 ResourcePool 承担租约、会话清理和部署预算，不为换名称再包一层池。调用官方 `Swoole\Coroutine\run()` 时须核对它默认补齐 `SWOOLE_HOOK_ALL` 的行为；线程业务沿用启动前确定的 hook，不在运行中改变进程级处理器。

## 配置与平台

- Swoole 选项沿用原名、单位和含义，并按实际接收它的 Server、Client、Socket 或运行时入口传入；不做一份逐项改名的配置镜像。框架资源/业务策略与原生选项分清归属，有冲突时在启动期明确拒绝或说明有效值。
- 自定义扩展键和 ABI 必须标明属于 TypeApp 补丁，不能当作官方机制传播。能力检查只约束使用该能力的入口，避免某项文件补丁成为纯网络或线程能力的无关前置。
- 原生线程池的线程数、扩容等待阈值、空闲回收时间各有含义；它们不等于排队条数、缓冲字节或任务硬截止。资源预算继续覆盖真实在途操作，超时不能提前归还额度。
- Windows、Linux、macOS 统一依赖 Swoole，按实际构建的能力选择入口。进程不可用时使用官方线程/协程；线程不可用时在当前执行单元内使用协程。这不是默认必须先开进程，也不允许用自建线程池、调度器或网络引擎填补差异。
- 经典 Server/Process 不可用时，HTTP/WS 采用官方协程 HTTP Server 与升级/帧能力，TCP/UDP 采用协程 Socket；线程构建需 PHP ZTS 和对应开关。独立命令在协程内使用官方 `SWOOLE_HOOK_PROC` 接管 `proc_open`、状态、终止与回收，参数数组不经 shell；管道是本地 IPC，不是网络 stream 回退。只有确切的必需能力缺失才报告启动错误，不以 Windows 名称直接否定官方通信能力。线程与协程不提供进程级故障隔离，降级后重新核对共享状态、硬停止、连接归属和资源总额。
- 跟进最新官方能力，发布时固定具体版本或提交、构建选项及源码摘要，升级后重验。官方主线支持、稳定发行与当前安装产物分别核对；不能自动追随未固定的 `master`，也不能把主线新增能力写成旧发行包已经具备。来源见[平台与工具链](../development/platform-support.md)。
- 先在 macOS ARM64 完成开发和真实行为验收，之后汇合其他正式目标。平台适配与补丁的可用性逐平台记录，不把仅一个平台的 ABI 检查写成全平台已支持。

## 原生补丁准入与撤除

每项新增或扩大的原生补丁必须在对应任务材料中给出以下证据；缺项就继续调查或保留候选状态，不进入默认基础路径：

1. 固定上游提交、原文件摘要、实际调用者和最小失败复现，说明是哪项已有契约不满足。
2. 已核对的原生 API/配置、框架侧最小调整，以及它们不能满足的具体边界；不能以“以后可能用到”作为理由。
3. 最小修改位置、影响的平台/ABI、失败与完成所有权，以及成功、拒绝、晚完成和退出回归。取消意图、停止等待、系统调用完成与资源可复用分别定义。
4. 维护责任归入既有组件和行为任务；升级时重验。上游等价修复或标准 API 足以覆盖时撤除补丁和自定义配置，再运行原行为回归。

不再把通用原生提交条数、字节上限或硬截止补丁作为所有 I/O 的前置条件。先使用 Swoole 原有配置、有限并发和应用资源所有权；只有真实调用者的实证缺口才增加窄范围适配。原生上限缺失不能自动成为另建工作池、定期扫描器、统计体系和线程回收协议的理由。永久不合作操作由独立于受阻业务线程的监督路径处理；若保留原生监督，必须单独证明已有角色监督不能覆盖，且不重复承担 Swoole 的线程回收职责。

## 实施与复核门槛

每次相关变更先在既有任务说明中列出“生产调用者 → 上游机制 → 项目必须补的职责 → 可删除的旧路径”。新增公共类、配置或原生补丁时解释其实际调用者、必要性及撤除条件，不另造一套审计系统。

复核最终差异时逐项确认：

- 网络等待、协议帧、定时唤醒及线程调度是否仍在应用侧重复实现；适用的原生能力是否已经复用。
- 迁移是否保持授权、协议错误、PSR、事务和恢复语义；需要底层原始输入才能判断的规则不能在原生解析丢失信息后假装补验。
- 配置是否保留原生语义；相同资源是否被多层重复计数或因线程扩展而放大；实际内存缓冲是否全部计入。
- 旧入口、调用者、配置、模板和文档是否一起迁移；非 Swoole 网络路径清理完成前，当前状态明确记为未完成，不能以“兼容模式”作为最终交付。
- 同平台、同功能、同负载下，外部行为、全量 AOT 和相关资源/性能检查是否成立。测试工具自身的独立协议客户端可保留，用来避免实现与验证共用同一错误。

方案审查和文档检查不替代实现验收；局部复现或编译消费者通过，不自动证明完整应用、性能或其他平台已经通过。
