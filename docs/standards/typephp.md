# TypePHP 0.9 语法与实现基线

本文是当前 TypeApp 构建入口的版本基线。生产代码、生成代码和实际安装的生产依赖均按锁文件交给 TypePHP AOT 编译；PHP 脚本测试只证明开发路径行为，不能替代原生编译和无源码运行验收。

## 锁定身份

- TypePHP：`v0.9.4`，提交 `874b82e96a2383712e8faf8177c6c715587e3546`
- PHPX：`v2.9.3`，提交 `a0138bbdd6cbfda62225adc56c558d0742114c8a`
- Swoole：固定开发快照 `4aff74a9ac086458d1c5251e71ac6e080f68b390`，运行时字符串 `6.3.0RC1`
- PHP：`8.5.10 ZTS`（目标平台 SDK 必须与实际 PHP、架构和线程模式一致）

准确依赖以根 `composer.lock` 和 `toolchain.lock.json` 为准；模板也必须携带相同的工具链身份。上面的 Swoole 提交是 RC1 后的开发快照，不能称为正式 6.3.0；正式版 6.2.3 也不能在没有重新构建和完整验收的情况下替换它。

TypePHP 0.9.4 的匿名类会回退到嵌入 opcode 或 `eval`，本仓构建入口明确拒绝该路径；生产实现使用具名类。静态 PHP embed 构建与源码是否全量 AOT 是两项独立检查，不能以嵌入业务字节码替代编译。Nano 的能力边界不覆盖当前应用的 Swoole、数据库及任务系统，本次不采用。

## 语言规则

TypePHP 使用严格编译边界：推断的标量局部变量使用固定原生存储；需要动态值或 PHP 引用时显式使用 `std::any()`、`std::ref()` 或 `toRef()`；编译期内置接口使用 `Type::*` 和 `std::*`，遵守锁定版本的编译期接口签名。函数、闭包和生成器入口写出完整参数与返回类型，属性明确初始化，生产代码不使用 `eval`、运行时源码加载或 Composer 解释回退。

编译器提供增量编译、翻译单元拆分和 Native 对象生命周期分析。应用不应依赖生成文件名、缓存目录或内部 C++ 符号；构建入口继续使用仓库声明的 `type-app.json`，以完整编译输入和产物清单作为验收边界。

嵌套 `unset` 由编译器生成单次操作链，保持 PHP 的求值顺序、缺失中间项不创建以及引用写回语义。业务代码直接使用正常 PHP 写法，无需在应用层复制数组或增加通用运行时补丁。

## 对象默认参数的编译适配

TypePHP 0.9.4 生成 `new Outer(new Inner())` 默认参数时，只保存最终表达式，可能丢失嵌套构造的临时声明和求值语句。`Type\Build\TypephpCompatibility` 为此复用上游独立函数上下文，将声明、按序求值、返回对象及清理放入同一默认值工厂；具名类构造、普通方法及函数继续使用原签名。

上游 Zend 包装入口还会把默认值工厂作为 C++ 调用实参而提前求值。兼容层在此入口按 PHPX 的参数缺失判断选择分支，包括命名参数跳位的 `IS_UNDEF`；显式参数或 `null` 不执行默认构造。对象每次省略参数重新创建，内层构造异常立即传播，不继续构造外层对象。

这些修正只作用于构建期，核对锁定版本及实际源码摘要，不改共享 SDK、应用源码或 `vendor`。`composer test:native-defaults` 使用同一夹具对照 PHP 与原生程序，覆盖构造顺序、对象身份、异常、命名参数、显式 `null`、标量引用和普通数组默认值，并在删除输入源码后执行产物。此项不包含闭包默认值，也不支持上游仍无法生成的“引用参数以对象数组为默认值”；不能据此声明任意 PHP 包兼容。

该修复不改变已发布 RC14 的字节；旧版独立应用需要安装包含修复并固定身份的构建组件。升级上游后，应先移除本适配进行同一组 PHP/原生回归，确认两处缺口均被覆盖，再删除对应摘要门禁。业务包的全量 AOT 与实际签发、验签等流程仍须单独验收。

## 继承构造器提升属性的作用域

TypePHP 0.9.4 为普通 Zend 类生成提升属性赋值时，PHPX 的 `setProperty()` 使用实际对象类作为写入作用域。子类继承父构造器时，父类的 `private` 属性可能被错误写成子类动态属性，随后父方法无法读取已声明的属性槽。

兼容层复用上游带声明作用域的属性写入入口：普通类使用构造器声明类，trait 使用组合后的实际声明作用域；写入仍在构造体之前完成，类型、可见性与 `readonly` 由 Zend 检查。Native ABI 的字段生成保持上游实现，不新增运行时反射或源码加载。

`composer test:native-promoted-property` 对照 PHP/AOT，覆盖抽象父类、多层继承、显式父构造调用、trait、公共/受保护属性、默认对象身份、私有槽和只读写入拒绝。父子同名属性仍受锁定 TypePHP 的属性遮蔽限制，本项不放宽。适配绑定提升赋值、属性处理及构造生成的源码摘要；上游升级后通过同一回归再撤除。原始 RC14 不包含此修复，独立应用须使用固定构建候选重新全量编译。

## 接口 self 常量的编译适配

TypePHP 0.9.4 在接口内解析 `self::` 时使用类专用名称入口，可能把 `Token\RegisteredClaims` 误解析为 `Token\`。例如接口中的 `ALL = [self::AUDIENCE]` 虽然可以编译链接，却会在原生程序进入 `main` 之前初始化失败。

`TypephpCompatibility` 仅在当前声明确实为接口时，将该次常量查找中的 `self` 规范化为接口完整名称，再交给上游解析；不改原声明 AST、常量注册顺序或普通类的 `self` 语义。适配核对预处理、作用域及常量解析源码摘要，`composer test:native-interface-constants` 对照 PHP/原生程序验证前向常量、嵌套数组、`self::class`、接口继承、实现类覆盖、命名空间隔离与全局接口。上游升级后用同一回归证明原实现已修复，再撤除适配；该结果不替代业务包完整运行验收。

## 类数组常量的原生符号隔离

PHP 类常量大小写敏感，方法名称大小写不敏感；`UNFINISHED` 数组常量与 `unfinished()` 方法可以同时声明。TypePHP 0.9.4 为两者生成相同的小写 C++ 名称时会导致编译歧义，只有大小写不同的多个数组常量也会相互碰撞。

兼容层为类和接口的数组常量分配独立存储符号，身份包含命名空间、声明类和保持大小写的常量名；声明、读取、请求初始化与清理以及线程存储使用同一符号。PHP 公开名称、方法分派、标量常量及访问权限仍由上游处理。`composer test:native-class-constants` 对照 PHP/AOT 检查同名方法、大小写常量、继承、接口、trait、动态读取和写时复制；原始最小输入也必须可直接编译，无需业务改名。适配绑定四个上游源码摘要，升级后通过同一回归再撤除。

## 已声明 toString 方法的编译适配

TypePHP 0.9.4 优先把 `toString()` 当作转换关键字，会将用户方法调用编译成 `php::toString()`。静态类型能解析到真实方法声明时，兼容层跳过关键字入口，继续使用上游方法分发；涵盖类、接口及父接口、继承、类型属性和函数返回值。

具体类在 `object`、`mixed`、引用或链式返回中被擦除时，零参数 `toString()` 根据实际对象的方法表查找真实声明，再通过既有 Zend/PHPX 调用入口执行 AOT 方法；保留词法可见性、原返回值及异常，接收者只求值一次。返回值不预先固定为字符串，方法 callable 也保留真实方法绑定。此路径不加载业务源码。

显式 `(string)`、插值及字符串拼接保持 `__toString()` 语义；没有声明 `toString()` 的对象和标量保留原转换行为。`composer test:native-declared-tostring` 与 `composer test:native-dynamic-tostring` 对照 PHP/AOT 检查上述分派、循环中的 builder 返回、空安全调用、权限拒绝、单次求值及异常身份。适配核对方法解析、转换、属性解析及声明查找的源码摘要；上游升级后须先验证同一行为再撤除。原始 RC14 和仅修复静态类型分派的旧候选不包含动态分派修复，独立应用须更新固定构建候选后重新全量编译。

## 数组引用参数的闭包捕获

TypePHP 0.9.4 把无默认值的 `array &$value` 编译为固定 `php::Array&`。局部闭包可使用 C++ 引用，但闭包传给其他调用者时需要 Zend 引用存储；上游会拒绝对该固定参数执行 `use (&$value)`。

兼容层复用上游捕获分析，仅将普通具名函数或方法中被闭包引用捕获的数组引用参数编译为已有 `php::Ref` ABI。PHP 参数签名与数组类型检查保持不变，调用侧引用桥接和异常写回继续由上游实现。闭包修改元素或替换整个数组后，即使抛异常，调用方也能观察到修改；业务若只在成功后替换原状态，仍需先使用独立候选副本。

`composer test:native-reference-capture` 对照 PHP/AOT 验证正常返回、异常写回、别名、私有方法、嵌套捕获、按值隔离、属性类型来源及入口类型拒绝。按值参数和未捕获的引用参数沿用原路径；强类型数组、Native ABI 与 Generator 不因本适配放宽。返回后仍持有引用的闭包要求调用方使用上游允许逃逸的动态存储，不能把固定 C++ 局部变量当作任意可逃逸引用；标量引用捕获不在本次范围内。

适配绑定参数解析、捕获分析、调用桥接和类型检查的源码摘要，不绕过固定存储的引用保护。独立应用需要固定累计构建候选后重新全量 AOT；原始 RC14 及旧候选字节不变。上游升级后以相同回归证明已覆盖该缺口，再撤除适配。

## 用户态调用实参的编译适配

包含本适配的构建组件允许普通用户函数、方法及 Zend 闭包接收额外位置参数。传入值完整保留；必需参数、标量和数组类型、未知命名参数仍检查，PHP 内部函数的数量规则不变。原始 RC14 构建器仍对非变参回调限制参数上限；独立应用需要使用固定身份的累计候选重新编译，已发布程序不会自行改变。

直接调用 `func_num_args()`、`func_get_args()` 和 `func_get_arg($position)` 时，数量取自当前调用，已声明位置读取当前局部参数值，额外位置保留原值；省略默认参数不增加数量，命名跳位和可变参数中的命名项沿用 Zend 规则。位置允许整数表达式，负值和越界抛出 `ValueError`；支持 `position:` 命名参数及函数导入别名。

编译器将需要内省的具名调用路由到已经 AOT 编译的 Zend 包装，保留引用参数、访问权限和晚绑定类。每个原生调用栈保存自己的 Zend 帧指针，递归、闭包及 Swoole 协程不使用共享参数栈；入口校验阻止意外读取外层帧。此路径不执行 PHP 源码，也不在业务调度器裁剪参数。

本项支持普通 Zend 函数、方法和闭包；Generator、Native ABI 中的参数内省明确拒绝。内省函数须直接具名调用（可使用导入别名），不支持把内省函数本身变成动态 callable，也不支持向内省函数动态展开参数。框架公开回调仍应声明合同中的完整签名；兼容既有事件合同不等于所有 PHP 调用形式均已覆盖。

`composer test:native-call-arguments` 对照 PHP/AOT 检查事件分派、默认值、命名参数、引用修改、递归、继承、闭包、异常后续调用及两个同时挂起的 Swoole 协程。调用分发、包装和优化器绑定同一组源码摘要，上游升级后须先通过上述回归再移除适配。

## embed 请求与模块生命周期

PHPX 2.9.3 的普通 embed 入口在请求启动后登记临时应用模块，退出时先卸载该模块，再调用 `php_embed_shutdown()`。错误处理器或原生回调仍持有业务对象时，后续对象清理可能读取已经释放的类元数据。Windows 教程的停服访问冲突已定位到这一路径；仅提前执行一次循环回收不能释放仍被引用的对象。

完整 embed 应用共用已有宿主：在 `php_module_startup()` 前登记应用模块，完成请求初始化后直接调用编译入口；退出依次结束请求、模块、SAPI 和线程存储。普通应用不因此启用业务线程或要求额外线程 SDK。`exit()` 由外层请求边界处理，保留退出码和析构；退出信号不进入业务 `catch`，也不执行被中断栈中的 `finally`，与 PHP 退出语义一致。不能在活动业务栈内提前卸载模块。扩展、SAPI 和 Nano 构建沿用其各自边界。

`composer test:native-embed-lifecycle` 对照 PHP/AOT 的闭包持有对象、析构及非零提前退出，并删除输入源码后运行同一程序。macOS 可用时附加系统 Guard Malloc，将提前释放类元数据的问题稳定转为访问失败；该检查不能替代 Windows 的完整教程、正常停止及同产物部署验收。适配绑定 TypePHP/PHPX 原文摘要，不修改共享 SDK。原始 RC14/RC15 及固定候选字节不变，独立应用须更新构建组件并重新编译。

## 内置函数警告与请求阶段

普通 embed 程序在模块初始化完成后进入编译业务；PHPX 2.9.3 的该入口未结束 PHP 的请求启动阶段，会把 `gzdecode(): data error` 等内置警告标为 `PHP Request Startup: data error`。应用将 warning 转为 `ErrorException` 时，该差异也会进入异常消息与业务日志。

共用 embed 宿主在请求初始化成功后、编译主入口分派前结束启动阶段，保留模块初始化期间的错误分类。函数名、严重级别和消息仍由 Zend 生成，不增加文本替换、错误屏蔽或应用错误策略；Swoole 线程入口继续负责各自请求阶段。

`composer test:native-builtin-warnings` 严格对照 PHP/AOT 的完整消息，覆盖直接与动态调用、多种内置函数、用户警告、warning 转异常、处理器恢复和后续成功调用，并在删除输入源码后运行。适配绑定 TypePHP 生成器和 PHPX embed 入口的源码摘要；上游升级后先验证相同行为再撤除。原始 RC14 与旧候选保持原字节，独立应用须更新固定构建候选并重新全量编译。

## PHPX 2.9 适配边界

PHPX 的调试实现在 `src/core/debug.cc`，并提供异常/转换策略头文件。TypeApp 仍只在独立、固定的 PHPX 源码副本上应用线程与协程隔离、finalizer bailout 和可写字符串副本适配；共享 `vendor` 或 SDK 不直接改写。适配原文摘要和唯一替换由 `Type\Build\PhpxThreadSource` 门禁，完成后必须重新编译整份 PHPX。

2.9.3 将 `Args::toArray()` 和 `Args::get()` 的实现移入 `src/core/base.cc`；版本升级须按实际源码审查迁移摘要，不能据此删除仍需要的语义适配。Windows 的 C 与 C++ 编译统一使用静态 CRT，并通过 TypePHP 的 `section_gc` 接口控制发布代码裁剪。当前候选与历史验收分开记录，见[本次升级证据](../evidence/typephp-upgrade-0.9.4.md)。

TypePHP 编译器的属性访问边界仍由 `Type\Build\TypephpCompatibility` 承接，适配只接受锁定版本的源码摘要。上游已实现的能力优先直接复用，新的版本升级若使适配不再必要，应先用等价回归用例证明后删除门禁和补丁。
